crystal-mod — валюта «Хрусталики» сайта Runes & Rails (NeoForge 1.21.1 / 21.1.228)

Структура и конвенции подогнаны под остальные моды в Xs_Mods (см. в первую
очередь "NEO auth-mod-json-with-hubs-and-webserver" — тот же принцип
конфига/HTTP-клиента, "NEO clans-mod" — сеть/меню):
  - плоский пакет ru.alex.crystalmod, без вложенных item/registry/command;
    единственное исключение — ru.alex.crystalmod.client (Screen/EditBox не
    существуют на выделенном сервере, их нельзя даже class-load'ить из кода,
    который сервер выполняет безусловно — см. javadoc CrystalModClient) и
    ru.alex.crystalmod.net (сетевые пакеты, тот же подпакет, что у clans-mod)
  - конфиг — свой JSON через Gson (config/Xs_Crystal/config.json), НЕ
    NeoForge ModConfigSpec/TOML
  - net.neoforged.gradle.userdev (не net.neoforged.moddev)
  - @Mod("crystalmod") + однопараметрический конструктор (IEventBus modBus)

Что делает
----------
- Предмет «Хрусталики» (банкнота, CrystalNoteItem) — не стакуется: у каждой
  свой serial (UUID) и value (номинал) в DataComponent. Это анти-дюп: сайт
  помнит статус каждого выпущенного serial'а и на повторную сдачу с другого
  аккаунта поднимает тревогу вместо повторного начисления.
- /crystal give <player> <serial> <value> — команда, которой сайт выдаёт
  банкноту по RCON при выводе хрусталиков в игру. Сигнатура зафиксирована в
  config.php сайта (crystals.give_command) — менять здесь без правки там
  нельзя.
- ПКМ по банкноте — депозит обратно на сайт (одна банкнота).
- /crystal check — держишь банкноту в основной руке, команда спрашивает сайт
  (action=verify_note), подлинная ли она, уже сданная (подозрение на дюп)
  или подделка (serial никогда не выпускался). Rate-limit 3/мин на игрока
  (RateLimiter — общая утилита, сам чистит память по неактивным игрокам).
- Банкомат (блок CrystalATMBlock, ПКМ → CrystalATMMenu):
    * Внести — кладёшь банкноты в лоток (до 5 слотов), вводишь сумму. Мод сам
      выбирает минимально достаточный набор банкнот (жадно, по возрастанию
      номинала), остальное остаётся в лотке. Если банкноты в сумме больше,
      чем нужно, — сдача минтится ОДНОЙ новой банкнотой с новым serial'ом от
      сайта (action=atm_deposit) и сразу выдаётся в инвентарь.
    * Снять — списывает хрусталики с баланса сайта (action=atm_withdraw) и
      выдаёт банкноты напрямую в инвентарь. RCON тут не участвует — банкомат
      физически рядом с игроком, доставка — просто ответ HTTP-запроса.
- Терминал рынка (блок MarketTerminalBlock, ПКМ → MarketListingMenu):
  кладёшь предмет в единственный слот, указываешь цену за штуку, жмёшь
  «Выставить лот». Предмет исчезает из инвентаря сразу (мод уже держит его
  физически, RCON-эскроу не нужен — action=create_listing_direct), лот
  становится активным на сайте сразу же.
- /crystal market listchest <registry_id> <quantity> <price> — та же прямая
  выставка лота, но для оп: смотришь на сундук (или любой Container-блок),
  команда изымает нужное количество и выставляет лот. При неудаче предметы
  возвращаются в те же слоты сундука.

Идемпотентность и «не жжём, пока не подтверждено»
--------------------------------------------------
Все мод-инициированные мутирующие вызовы (atm_deposit, atm_withdraw,
create_listing_direct) идут с tx_id (UUID), который генерирует мод при
СТАРТЕ операции. Сайт дедуплицирует по tx_id (crystal_idempotency,
crystals_common.php) — повтор с тем же tx_id просто возвращает сохранённый
результат, ничего не выполняя заново.

Критично: при СЕТЕВОЙ ошибке (таймаут/обрыв — то есть исход НЕИЗВЕСТЕН, сайт
мог и обработать запрос) мод обязан переиспользовать тот же tx_id на
следующей попытке, а не сгенерировать новый — иначе, например, «Снять»
спишет баланс дважды (там нет анти-дюп подстраховки по serial, как у
депозита). Именно поэтому CrystalATMMenu/MarketListingMenu хранят
pendingXxxTxId и на повторный клик после сетевой ошибки переигрывают ТУ ЖЕ
попытку, игнорируя новый ввод пользователя, пока не придёт определённый
ответ. При явном отказе сайта (ok:false, не сетевая ошибка) — предметы
безопасно возвращаются игроку.

Отдельно на сайте есть подстраховка от бага/гонки в самом моде: если
atm_deposit получит новый tx_id на банкноты, которые уже были обработаны
РАНЬШЕ под другим tx_id (fresh_credited=0), сдача повторно не минтится —
только предупреждение (см. crystals_common.php → crystalProcessDepositNotes,
crystals_api.php → action=atm_deposit). Найдено и исправлено при живом
тестировании на реальной БД в процессе разработки.

Про нагрузку и утечки
----------------------
- Ни у ATM, ни у терминала рынка НЕТ BlockEntity и тикера — весь временный
  инвентарь (лоток банкомата, слот терминала) живёт только в открытом меню
  (AbstractContainerMenu), закрытие меню возвращает несписанное игроку, как у
  ванильного верстака. Нечему тикать — нечему протекать.
- HTTP-вызовы асинхронны через один общий CrystalAPI-Async пул (кэширующий,
  daemon-потоки), не блокируют тик сервера.
- RateLimiter — общая карта на все вызовы /crystal check, а не по экземпляру
  на игрока; отдельный ScheduledExecutorService чистит неактивные записи
  каждые 10 минут, карта не растёт бесконечно.
- Кнопки Внести/Снять/Выставить лот блокируются флагом busy на время запроса
  — повторный клик не плодит параллельные запросы.

Настройка
---------
После первого запуска появится config/Xs_Crystal/config.json:

  {
    "apiBaseUrl": "https://runes-and-rails.ru",
    "apiSecret": "change_this_to_the_site_api_secret"
  }

apiSecret — то же значение, что и у AuthMod (config/Xs_Auth/config.json,
поле apiSecretKey) и что config.php → 'api_secret' на сайте.

IP сервера должен быть в белом списке файрвола API сайта (админка → API
firewall) — иначе новые эндпоинты (crystals-deposit/crystals-atm/
crystals-verify/crystals-listing в FIREWALL_CRITICAL, api.php) вернут 403.

Что осознанно не сделано
-------------------------
- Игрок офлайн при /crystal give — команда просто зафейлится (sendFailure),
  но RCON поверх TCP это НЕ разрыв соединения, а обычный ответ — сайт его не
  разбирает и посчитает доставку успешной, хотя банкнота никуда не попала.
  Первая осмысленная починка — научить сайт заранее проверять, онлайн ли
  игрок (как Donate::checkOnline() в donate.php), прежде чем звать RCON.
- Пачечный депозит по ПКМ — эндпоинт deposit уже принимает массив notes за
  один запрос, CrystalNoteItem пока шлёт по одной банкноте (для банкомата это
  уже не так — там пачка).
- Банкомат/терминал рынка не проверяют реальную дистанцию до блока
  (stillValid всегда true) — минимальная защита от читерского открытия меню
  без блока рядом, не критично для доверенного окружения, но стоит доделать
  при появлении читов на клиенте.
- Лоток банкомата — 5 слотов (макс. 500 хрусталиков за один Внести, банкноты
  по 100). Для больших сумм — несколько заходов либо увеличить TRAY_SIZE.

Сборка
------
./gradlew build   (JDK 21, тот же тулчейн, что у остальных NeoForge-модов
                    папки — см. auth-mod/clans-mod)

Не собирался в среде, где написан (нет сетевого доступа до Maven Central /
NeoForge maven в песочнице) — код сверен построчно с рабочими классами
AuthMod/AuthAPI/ConfigManager (структура), ClansMod (сеть/меню-конструктор) и
GimpanumMod SealContents/SealItem (Codec/DataComponent-паттерн), но перед
деплоем стоит собрать и поднять runServer локально. Экраны банкомата/рынка —
без текстуры фона (простые guiGraphics.fill() прямоугольники вместо
переиспользования ванильной GUI-текстуры) именно по этой причине: пиксельная
раскладка слотов не проверена визуально, грубый фон надёжнее потенциально
съехавшего.
